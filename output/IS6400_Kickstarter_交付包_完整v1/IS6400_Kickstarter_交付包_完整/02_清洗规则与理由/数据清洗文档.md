## 二、清洗原则

1. **行级只删「明确错误」与「没有可用结果」的行**，不删任何可能改变结论的样本；
2. **值级只做标准化，不改语义**：类型纠正、大小写归并、引号折叠、口径统一；
3. 无法判定为错误的问题（缺失、极端值、口径冲突）一律**保留 + 打标记**；
4. **不覆盖原始列**：所有标准化结果与派生特征都写成新列，原始列原样保留（可核对、可回滚）；
5. 每个被删除的行都进入审计文件（id + state + 原因）；
6. 清洗结果写入**新文件**（默认 `ks_clean.csv`），原始 CSV 永不被修改。

### R1 未开始 / 未结束记录

- **删除理由**：这些记录**没有可用的成败结果**：`live` / `submitted` / `started` 的募集尚未结束（右删失），`suspended` 被平台中止。把未结束当成失败会让成功率被系统性低估，而成功率是本项目所有分析的基准。
- **不删的代价**：若保留，必须为它们单独定义标签，否则任何 success rate 计算都会失真；`canceled` 已按决定保留为独立第三类，不参与成功率计算（`succ` 记为缺失）。

### R3 目标金额非法

- **判定条件**：`goal <= 0`
- **本步删除**：0 行（按顺序执行，为增量计数，不重复计算重叠原因）
- **删除理由**：`goal` ≤ 0 时 `log(goal)` 无定义，目标金额分箱与「目标越高越难」的单调性检验都会失效；这类记录本身多为未填写目标的草稿。
- **不删的代价**：若把它们塞进最低金额档，会人为拉高该档成功率，削弱核心结论。

### R4 截止时间非法

- **判定条件**：`deadline 解析失败 / <=1970-01-02 / dur <= 0 / dur > 365`
- **本步删除**：0 行（按顺序执行，为增量计数，不重复计算重叠原因）
- **删除理由**：`deadline` 无法解析 / 1970 / 早于上线时间 / 时长 >365 天，意味着项目时长不可计算或荒谬；时长是仅次于目标金额的第二大杠杆（8–14 天 70.9% vs 46–60 天 28.4%）。
- **不删的代价**：若保留，时长分箱会出现负数与「50 年」这类异常值，均值与分箱结论都不可信。

- **不删的代价**：保留会让募款额均值、对数变换（负值无定义）以及完成率派生列全部出错。

## 四、值级清洗：字段标准化（不删行，逐项 + 理由）

### V1 时间字段：混合编码解析

- **问题**：`created_at` / `deadline` 同时存在 `'2020-11-07 01:56:31 UTC'` 字符串与 epoch 秒数字两种编码；`launched_at` 是 float epoch，其中 11,405 行为 1970 占位值。
- **处理**：新增 `launch_dt` / `deadline_dt`（ISO 时间）与 `dur_days`；原始三列保留。
- **理由**：不解析就算不出项目时长、做不了季节性（月/星期/小时）、无法时间切分与趋势分析。

### V2 布尔字段：类型规范化

- **问题**：`spotlight` 与 `staff_pick` 本身是**布尔值**，但因为存在缺失（NaN），读入后 dtype 退化成 **object**（真值分布：`spotlight` = {'False': 386819, 'True': 297327, 'nan': 9916}；`staff_pick` = {'False': 608978, 'True': 72883, 'nan': 12201}）——既不是布尔类型，也不能直接做 `.sum()` 等布尔运算。
- **处理**：统一转为**可空布尔**（`boolean` dtype：`True` / `False` / 空）。
- **理由**：object 列上做布尔判断/求和会报错或给出意外结果，建模时也需要明确的布尔或 0/1。
- ⚠️ **踩过的坑**：不要用 `{'True': True, 'False': False}` 这类字符串字典去 `.map()` 这两列——值是**真布尔**，字符串键匹配不上，结果会整列变成缺失。
- ⚠️ **CSV 的局限**：CSV 不存储「可空布尔」类型，把文件重新读入后这两列仍是 object（`True` / `False` / 空）。需要布尔运算时请显式 `astype('boolean')`，或读入时指定 `dtype={'spotlight': 'boolean', 'staff_pick': 'boolean'}`；同理，所有时间列在 CSV 里都是字符串。

### V3 品类标签：大小写归并

- **问题**：同一个品类存在两种拼写。一级品类 `category_parent_name`：16 → 15（可合并 1 个，即 `Comics` / `comics`）；细分品类 `category_name`：**218 → 146（可合并 72 个）**。
- **处理**：新增 `category_key`（一级）与 `subcategory_key`（细分），按小写 + 去空白归并；缺失记 `unknown`。原始列保留。
- **理由**：不归并时按品类分组会产生重复条目——第一版图表上确实冒出过「comics 13.4% (n=157)」这样一个假点；细分层 72 个重复标签的后果同样严重。

### V4 文本字段：引号异常折叠

- **问题**：`name` 27,455 行、`blurb` 34,050 行含双引号，其中存在 `""""标题""""` 这类连续 4 个引号的重复转义（`name` 27,455 行 / `blurb` 34,050 行）。
- **处理**：新增 `name_clean` / `blurb_clean`，把**连续 2 个以上**的双引号折叠为一个；原始列保留。
- **理由**：这是抓取时的重复转义产物，会污染分词（`""""millionaire` 会变成带引号的 token）；折叠后文本才可直接进 TF-IDF。

### V5 国家字段：口径统一

- **问题**：两个国家字段含义不同——`country` 是**平台开通市场**（25 个取值），`location_country` 是**地理编码结果**（225 个标准二字码，含属地）；实测 31,900 行（4.61%）两者前两位不一致。
- **处理**：新增 `country_final`（优先 `country`，缺失回退 `location_country`）与 `country_mismatch` 标记。
- **理由**：跨国分析必须先选定一个口径；两者都保留则任何按国家的分组都会有两种答案。（注：早期文档曾猜测 `location_country` 的 225 个取值是「地区名/拼写变体混入」，实测**不成立**——它全是标准二字码。）

### V6 文本外层空白：已核验，无需处理

- 实测 8 个文本字段（品类、国家、币种、州名等）的外层空白行数全部为 **0**。
- 仍然在 `category_key` / `subcategory_key` / `name_clean` / `blurb_clean` 里统一做了 `strip()`，作为防御性处理。

### V7 极端小目标金额：标记而非删除

- **问题**：全表 `goal` < 1 的有 9,649 行，其中终态（successful / failed）3 行；最小值为 0 / 0.01 / 0.15 / 0.5。
- **处理**：保留，新增 `goal_under_1` 标记列；另保留 `goal_capped`（99.9 分位截断）。
- **理由**：这类记录可能是「测试项目」也可能是真实的小额项目，无法判定为错误；删除会损失真实样本，直接入模又可能影响分档，所以交给建模阶段用标记自行取舍。

### V8 缺失值策略

| 字段 | 缺失率 | 策略 | 理由 |
| --- | ---: | --- | --- |
| `category_name` / `category_id`（细分品类） | 18.97% | `subcategory_key = 'unknown'` | 缺失非随机，删行会造成选择性偏差 |
| `category_parent_name`（一级品类） | **0%** | 无需处理 | 建模实际使用的就是这一列 |
| `profile_blurb` | 85.11% | 保留列、不做文本特征 | 发起人档案文本，非项目文本 |
| `profile_name` | 5.23% | 保留列 | 与 `name` 高度冗余 |
| `usd_pledged` | 1.64% | 保留（分析用 `pledged` 或标记） | 泄漏列，仅描述统计用 |
| `blurb` | 0.02% | 保留 | 文本分析主力字段 |
| 其余 36 列 | ≤3.3% | 保留原值 | 缺失比例低，按需在建模阶段处理 |
